## Objetivo

Fazer a OpenAI produzir TravelQueryMeaningV2 em structured output sem alterar respostas ou tools.

## Contexto

O contrato e o validator factual V2 devem estar prontos antes do provider.
O V1 continua funcionando.

O OpenAI Travel Interpreter V2 é responsável por interpretar linguagem
natural aberta, incluindo:

- origem e destino;
- papel de localidades;
- deíxis;
- papel contextual de números;
- UF versus palavra comum;
- ambiguidade entre opções;
- preferência temporal relativa.

O validator não deve reconstruir essas interpretações por regex, tokens,
pontuação ou conectores. Ele apenas valida o resultado estruturado contra
contrato, facts, catálogo, estado e invariantes.

### Dependência consolidada após o sexto review

O shadow fornece `OptionReference`, papéis de localidade, UF explícita,
deíxis e clarification já interpretados. Não pode depender de
`ValidateTravelQueryMeaningV2` para corrigir ou redescobrir significado a
partir de `CurrentTurn`. O validator pode rejeitar `INDEX` fora do range,
`DATE` invisível, `DEICTIC` ambíguo ou localidade sem fact inequívoco, mas não
escolhe outra interpretação. A dependência do 3.6F-B foi satisfeita e o 3.6F-C
foi concluído após review final sem P1/P2.

## Escopo autorizado

Schema V2, prompt V2, runner/mapper V2, shadow V2 e testes. Sem runtime influence, tool calls ou state mutation.

## Implementação

1. Criar schema JSON strict V2.
2. Criar prompt compacto com:
   - current turn;
   - canonical state mínimo;
   - active prompt;
   - facts atuais resumidos;
   - catálogo resumido quando necessário;
   - exemplos semânticos mínimos;
   - instrução explícita para distinguir o papel contextual de números,
     UF, conectores, origem/destino e deíxis.
3. Preservar:
   - `store=false`;
   - `tools=[]`.
4. Mapear JSON para `TravelQueryMeaningV2`.
5. Rodar `ValidateTravelQueryMeaningV2` somente como validator factual:
   - schema e shapes;
   - datas e opção contra facts;
   - catálogo e ambiguidade factual;
   - estado e DecisionStrength;
   - ausência de side effects.
6. Persistir somente resumo sanitizado em shadow.
7. Não persistir body bruto, documentos ou dados sensíveis.
8. V1 e V2 podem rodar lado a lado sem segunda resposta ao cliente.
9. No máximo uma chamada V2 por turno.
10. Cobrir em shadow, no mínimo:

```text
"opção 1 ou 2"
→ OptionReference NONE ou clarification explícita

"opção 3"
→ OptionReference INDEX=3, ainda que o validator rejeite por range

"daqui a 2 dias"
→ referência temporal, nunca INDEX

"quero a opção 2 no dia 15"
→ INDEX=2 e data mencionada separadamente

"Santa Cecilia se tiver vaga"
→ cidade sem UF explicitamente informada

"Santa Cecilia/SE"
→ cidade com UF SE

"de Fraiburgo para Santa Ines"
→ origem Fraiburgo e destino Santa Ines
```

## Critérios de aceite

- Nenhuma mudança user-visible.
- Nenhuma tool executada.
- O OpenAI V2 interpreta corretamente origem/destino, papel de números,
  UF versus conjunção, deíxis, ambiguidade de opções, coverage,
  institucional e poltrona.
- Os casos adversariais definidos no plano aparecem corretamente no shadow.
- O validator não reinterpreta o texto para corrigir o provider.
- Schema inválido/erro vira skipped/rejected seguro.
- Dados sensíveis não entram no resumo.
